# RedMind-AI — Project Reference (for AI/automated consumption)

> Generated by direct codebase inspection (not by reading marketing copy or comments).
> Purpose: give any AI assistant or new contributor a ground-truth map of what this codebase
> actually does, as opposed to what its UI claims it does. Where the two diverge, this doc
> flags it explicitly under "Known Gaps."

---

## 0. One-paragraph summary

RedMind-AI is a local VAPT (Vulnerability Assessment / Penetration Testing) demo tool: a
single-file vanilla-JS dashboard (`frontend/dashboard.html`) that drives a thin FastAPI backend
(`main.py`). The backend dynamically loads one Python file per "check" from `modules/` and
executes a `run(target, timeout, dangerous)` function that fires live HTTP requests at a target
URL using `requests`. There is no database — all scan history/results persist in browser
`localStorage`. The catalog advertises 179 named vulnerability checks, but the actual module
code only implements **8 distinct payload behaviors**, templated across ID ranges.

## 2. Backend — `main.py` (FastAPI)

Single file, ~108 lines. This is the entire live backend.

### 2.1 Startup / middleware
```python
app = FastAPI(title="RedMind-AI VAPT Scanner")
app.add_middleware(CORSMiddleware, allow_origins=["*"], allow_methods=["*"], allow_headers=["*"])
app.mount("/static", StaticFiles(directory="frontend"), name="static")
```
- CORS is fully open (`*`). Fine for local demo, not acceptable if ever exposed publicly.
- `/static` mount exists but is not actually used by the dashboard's own asset loading (dashboard
  is served inline as HTML, not via the static mount).

### 2.2 Endpoints

| Method | Path | Request body | Response | Purpose |
|---|---|---|---|---|
| GET | `/` | — | raw HTML | Reads and returns `frontend/dashboard.html` as a string (`open(...).read()`), served as `HTMLResponse`. Not templated — pure static passthrough. |
| POST | `/run` | `{"module_id": str, "target": str, "context": dict}` (Pydantic `RunRequest`) | `{"module_id": str, "result": {...}}` or `{"error": str, "result": null}` | **The only endpoint the live dashboard calls.** Dynamically imports `modules/{module_id}.py` via `importlib.util.spec_from_file_location`, calls `mod.run(target=target, timeout=10, dangerous=True)`, returns the module's result dict. `context` field is accepted but never used. Timeout is **hardcoded to 10** here regardless of what the frontend/registry says. |
| WS | `/ws` | JSON `{"target": str}` on connect | streamed `{"progress": int, "msg": str}` frames | **Legacy / dead path.** Shells out via `subprocess.run(["powershell", ..., "run_all_modules.ps1", "-Target", target, "-Checks", "checks_runtime.json"])`. Windows-only (calls `powershell` directly). Parses stdout as JSON if possible. **The current dashboard.html never opens this socket** — it only uses `/run`. Keep this in mind before assuming WS is part of the live flow.

### 2.3 Module execution contract
Every file in `modules/` must expose:
```python
def run(target: str, timeout: int, dangerous: bool) -> dict:
    return {
        "check_id": "RM-CHK-XXX",
        "severity": "CRITICAL" | "HIGH" | "MEDIUM" | "LOW" | "INFO",  # hardcoded at generation time, not computed from result
        "target": target,
        "dangerous": bool,
        "findings": [ { ... free-form dict per finding ... } ],
        "summary": {"tested_requests": int, "positive_hits": int}
    }
}
```
No shared base class or interface enforcement — this is a duck-typed convention only. If a
module raises, `main.py`'s `/run` handler catches the exception and returns a synthetic
`INFO`-severity error result rather than propagating the HTTP error.

## 3. Module generation — how the 179 "checks" actually came to exist

`generate_modules_fixed.py` is the source of truth for what's in `modules/`. It defines **exactly
8 payload template functions** and stamps them across ID ranges with only `check_id` and
`severity` substituted:

| ID range | Payload function | Behavior | Severity assigned |
|---|---|---|---|
| RM-CHK-001–020 | `admin_payload()` | GET `/setup`, `/admin/setup`, `/install`, `/initialize`, `/api/setup`; flag any 200 | CRITICAL |
| RM-CHK-021–040 | `xss_payload()` | GET `?q=<script>alert(1)</script>`; flag if payload reflected verbatim | HIGH |
| RM-CHK-041–060 | `auth_payload()` | GET target; check `Set-Cookie` header for missing `HttpOnly`/`Secure` | HIGH |
| RM-CHK-061–080 | `idor_payload()` | GET `target/1` and `target/2`; flag if both return 200 | HIGH |
| RM-CHK-081–100 | `traversal_payload()` | GET `?file=../etc/passwd`; flag if `root:x` appears in response | CRITICAL |
| RM-CHK-101–120 | `ssrf_payload()` | GET `?url=http://169.254.169.254`; flag if status in [200,500] | CRITICAL |
| RM-CHK-121–150 | `api_payload()` | POST to target; flag any 200 as "method tampering" | MEDIUM |
| RM-CHK-151–179 | `header_payload()` | GET target; flag if `X-Frame-Options` header absent | LOW |

**Consequence:** RM-CHK-001 and RM-CHK-002 run byte-identical logic (verified via `diff`); only
`check_id` differs. This is true for every pair within the same range. The frontend's
`VULN_NAMES` map (see §4.3) assigns 50 distinct human-readable vulnerability names (SQL
Injection, JWT Algorithm Confusion, GraphQL Introspection, Django Secret Key Exposure, etc.) to
IDs that share one of the 8 generic payloads above — **the named vulnerability and the executed
code are frequently unrelated.**

`modules_legacy/` shows an earlier, more honest attempt (e.g. `rm_mod_002_sqli.py` distinct from
`rm_mod_002.py`) that was apparently abandoned in favor of the bulk-templated regeneration.

`attack_knowledge.py` is a separate static dict (`ATTACK_KNOWLEDGE`, keyed by check_id) holding
CVSS guesses, descriptions, detection signatures, and mitigation text for reporting purposes.
It is **not read by `main.py` or `dashboard.html` at runtime** — it exists as source material for
manually-written reports, not as live logic.

## 4. Frontend — `frontend/dashboard.html`

Single file (~1460 lines): inline `<style>`, inline `<script>`, no build tooling, no framework.
Runs directly by opening the HTML or being served at `GET /`.

### 4.1 Backend connection
```js
const API = () => document.getElementById('settingsApiUrl')?.value || 'http://127.0.0.1:8000';
```
The backend base URL is a **mutable text input on the Settings page**, not a build-time config.
Default value is `http://127.0.0.1:8000`. There is no `.env`, no config file — the only source
of truth for "where is the backend" is this DOM element's current value (persisted nowhere
unless the user's browser retains form state).

### 4.2 Pages / navigation
Single-page app via `navigate(pageId)` toggling `.active` class on `.page` divs:
`dashboard`, `newscan`, `results`, `history`, `reports`, `settings`. Keyboard shortcuts:
`n`/`d`/`h`/`r` to jump pages, `Ctrl+B` to toggle sidebar.

### 4.3 Client-side catalog (independent of backend)
- `ATTACK_CATALOG`: hardcoded JS array of `{id, name, cat, sev}` for named checks (RM-CHK-001
  through RM-CHK-056 explicitly listed), then a `fillCatalog()` IIFE auto-fills RM-CHK-057
  through RM-CHK-179 as generic `Security Check #N` entries cycling through category/severity
  arrays.
- `VULN_NAMES`: maps ~50 IDs to display names (only used for reporting/labels, not tied to
  actual module logic — see §3).
- `REMEDIATIONS`, `getVulnDesc()`: static remediation/description text keyed by ID, with
  fallback generic text for unmapped IDs.

### 4.4 Scan execution flow — `startScan()`
1. Reads `target` input and `scanType` radio (`quick` | `web` | `network` | `custom` | `full`).
2. Resolves module list:
   - `quick` → first 20 IDs
   - `web` → first 60 IDs
   - `network` → hardcoded list `['RM-CHK-009','RM-CHK-013','RM-CHK-014', ... 'RM-CHK-040']`
   - `custom` → whatever's checked in `selectedAttacks` (Set)
   - `full` → all 179 IDs
3. Resets UI (progress bar, live counters, log panel, timer interval).
4. **Sequential loop** (no concurrency):
   ```js
   for each modId in modules:
     fetch(`${API()}/run`, {
       method: 'POST',
       headers: {'Content-Type':'application/json'},
       body: JSON.stringify({module_id: modId, target, context: {}})
     })
     // normalizes severity casing via SEVERITY_MAP
     // if findings.length > 0: increments liveCounts, appends to findings[], logs to scanLog
   ```
   A full scan = 179 sequential round-trips (browser → FastAPI → dynamic import → live HTTP
   request to target → back). No batching, no `Promise.all`, no worker pool. `scanAborted` flag
   checked each iteration lets the user stop early via `stopScan()`.
5. On completion: computes `riskScore = CRITICAL*25 + HIGH*12 + MEDIUM*6 + LOW*2 + INFO*0.5`
   (capped at 100, via `computeRiskScore()`), `secScore = 100 - riskScore`, builds a `scanRecord`
   object, and writes it to two `localStorage` keys:
   - `rm_last_results` — most recent scan (single object)
   - `rm_scan_history` — array capped at 50 entries (`unshift` + `length=50`)
6. No server-side persistence exists anywhere. Refreshing/clearing localStorage loses all history.

### 4.5 Severity normalization
`SEVERITY_MAP` / `normSev()` coerces any casing variant (`Critical`, `critical`, `CRITICAL`) to
canonical uppercase, defaulting unknowns to `INFO`. Applied client-side to whatever the module
returned — severity is never recalculated from finding content, only relabeled for display.

## 5. Standalone / auxiliary scripts (not part of the live `/run` flow)

| File | What it does | Wired into main.py? |
|---|---|---|
| `run_all_modules.py` | CLI: `--target URL --checks path.json`, iterates `checks_runtime.json`-style registry, `importlib.import_module(f"modules.{id}")`, aggregates severity counts, prints progress bar | No — invoked only via `run_all_modules.ps1`, which itself is only invoked by the legacy `/ws` handler |
| `run_all_modules.ps1` | Activates `.venv`, calls `run_all_modules.py` | Only reachable via `/ws` (dead path per §2.2) |
| `vapt_config.py` | Builds `VAPT_CHECKS` list: for `MODE="DEMO"`, enables only checks 1–40 with short timeouts (5s for 1–20, 3s for 21–40); for `MODE="FULL"`, enables all 179 with range-based timeouts (SQLi 1–20→15s, XSS 21–40→8s, Auth/IDOR 41–80→10s, SSRF/RCE 81–120→20s, Logic/Config 121+→10s) and `dangerous=True` for IDs 1–120 | Feeds `export_checks.py` → `checks_runtime.json`, consumed only by `run_all_modules.py`/legacy WS path — **not** by the live `/run` endpoint (which hardcodes `timeout=10, dangerous=True` for every call regardless) |
| `export_checks.py` | Dumps `VAPT_CHECKS` to `checks_runtime.json` | Manual/offline step |
| `echo_app.py` | Flask app with paired safe/vulnerable Jinja2 templates (`SAFE_TEMPLATE` uses `{{ q }}`, `VULN_TEMPLATE` uses `{{ q|safe }}`) plus a `SQLSIM_TEMPLATE` for simulated SQL error output | This is a **test target** to scan against, not part of the scanner itself |
| `tools/discover_endpoints.py`, `tools/probe_candidates.py` | Standalone recon helpers | Not called by any other file in the repo |

## 6. Data flow diagram (single check, live path only)

```
Browser (dashboard.html, startScan loop)
   │  fetch POST /run  { module_id, target, context: {} }
   ▼
FastAPI main.py  →  importlib.util.spec_from_file_location(module_id, "modules/{id}.py")
   │
   ▼
modules/RM-CHK-XXX.py :: run(target, timeout=10, dangerous=True)
   │  requests.get/post(target + payload_suffix, headers={"User-Agent": "RedMind-AI-VAPT/1.0"})
   ▼
Live HTTP request → actual scan target
   │
   ▼
{check_id, severity(hardcoded), target, dangerous, findings[], summary}
   │  ← JSON response
   ▼
Browser: normalize severity → update liveCounts/log/progress bar
         → on scan end, write scanRecord to localStorage (rm_last_results, rm_scan_history)
```

Repeated once per module ID in the selected profile, strictly sequentially, no retries beyond
the `except Exception: pass` inside each module's own request calls.

## 7. Configuration surface (everything that's actually configurable)

| Setting | Where it lives | Effect |
|---|---|---|
| Backend base URL | `dashboard.html` Settings page input `#settingsApiUrl` (in-memory DOM only) | Determines where `fetch` calls go |
| Per-module timeout (legacy path only) | `vapt_config.py` → `checks_runtime.json` | Only respected by `run_all_modules.py`; **ignored by the live `/run` endpoint**, which hardcodes `timeout=10` |
| `dangerous` flag | Hardcoded `True` in `main.py`'s `/run` handler; independently configurable per-check in `vapt_config.py` for the legacy path | Modules receive it but most modules don't branch on it — it's accepted but frequently unused inside `run()` bodies |
| `MODE` (DEMO/FULL) | Top of `vapt_config.py`, manually edited | Only affects which checks are `enabled` in the legacy CLI/WS flow |
| Scan profile (quick/web/network/custom/full) | Radio buttons in dashboard, resolved client-side | Only client-side list-slicing of `MODULES_FULL` — no backend awareness of "profiles" |

## 8. Known gaps / risks (ground truth vs. presentation)

1. **Catalog inflation:** 179 labeled "checks" reduce to 8 executed behaviors (§3). Any named
   vulnerability outside {admin-endpoint probe, reflected XSS, cookie flags, naive IDOR, path
   traversal, SSRF probe, method tampering, missing X-Frame-Options} has **no real detection
   logic** despite appearing in `VULN_NAMES`/`ATTACK_CATALOG`.
2. **Static severity:** severity is baked in at code-generation time per ID range, not computed
   from actual finding evidence. Two targets with wildly different real risk get identical
   severity labels per check.
3. **Dead code paths:** `/ws`, `run_all_modules.ps1`, `checks_runtime.json`, and `vapt_config.py`
   form a complete parallel pipeline that the live dashboard **never calls**. Anyone reading
   `vapt_config.py`'s timeout/dangerous logic and assuming it governs the live scan flow will be
   wrong — `main.py`'s `/run` hardcodes its own values.
4. **No persistence layer:** all results live in browser `localStorage`; there is no database,
   no multi-user support, no server-side scan history.
5. **Windows coupling:** the only concurrent/background scan path (`/ws`) shells out to
   `powershell.exe` directly — won't run on Linux/macOS hosts.
6. **Open CORS + no auth:** acceptable for a local FYP demo; not acceptable if this is ever
   deployed reachable from a network other than localhost.
7. **Config never reaches modules:** `context` field in `RunRequest` is accepted by the API but
   never passed to or used by any module's `run()`.
